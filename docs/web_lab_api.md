# ЛР по Web: проектирование REST API

Основной артефакт лабораторной — [openapi.yaml](../openapi/openapi.yaml).
Спецификация использует OpenAPI 3.1.0; каждый ключ `paths` начинается с
`/api/v1/`.

## Проверка

Для линтинга и проверки примеров без реализации backend выполните из корня
проекта в WSL. Требуются Node.js, Redocly CLI (`npm install --global @redocly/cli`)
и GNU Make:

```bash
make openapi-check
```

Скрипт запускает Redocly lint, создаёт временный полностью разрешённый bundle
и проверяет примеры JSON по `required`, типам, enum, ограничениям строк/чисел,
форматам `email`/`date-time`/`uri` и `additionalProperties`. Дополнительно для
каждой операции проверяются успешный ответ `2xx`, `400` для операций с входными
параметрами, `500` для внутренней ошибки, наличие схемы у каждого тела ответа и
отсутствие тела у `204 No Content`.

После изменения контракта Go-интерфейс, модели и chi-router обновляются командой:

```bash
make openapi-generate
```

## Почему это REST

- `channels` — коллекция: `GET /api/v1/channels` и `POST /api/v1/channels`;
  ресурс канала: `GET/PATCH/DELETE /api/v1/channels/{channelId}`. Это полное
  CRUD-покрытие одной сущности.
- `PATCH /api/v1/channels/{channelId}` с телом, содержащим только
  `description`, — пример частичного обновления. `minProperties: 1` запрещает
  пустое обновление.
- Подписка и рейтинг представлены ресурсами-связями: `PUT` создаёт или заменяет
  связь, `DELETE` удаляет её. Просмотр — `POST` в коллекцию событий
  `/videos/{videoId}/views`.
- Публикация видео — состояние подресурса
  `/videos/{videoId}/publication`, изменяемое через идемпотентный `PUT`, а не
  RPC-путь `confirm`.
- `/auth/*` оставлен action-oriented только для операций с учётными данными,
  которые не являются CRUD-операциями над предметным ресурсом.

## Отдельный контракт загрузки

Для передачи большого бинарного файла REST API не проксирует тело через себя:

1. Клиент вызывает `POST /api/v1/channels/{channelId}/videos/uploads` и получает
   pending-видео и временный `uploadUrl`.
2. Клиент выполняет `PUT` бинарного файла на `uploadUrl` с
   `Content-Type: application/octet-stream`.
3. Клиент вызывает `PUT /api/v1/videos/{videoId}/publication` с
   `{ "status": "published" }`.

Это отдельный HTTP-контракт object storage, а не новый ресурс нашего API. SSE,
WebSocket, gRPC или webhook не требуются: в заявленном функционале нет
непрерывного серверного потока или двунаправленного сеанса.

## HTTP-решения для защиты

Используются `Authorization: Bearer`, `Content-Type`, `Accept`,
`X-Request-ID`, `Location` для `201 Created`,
`Cache-Control` для публичных GET и `Retry-After` для `429`. Основные ответы:
`200` — представление ресурса, `201` — создан ресурс, `204` — успешное действие
без тела, `400` — ошибка запроса, `401` — нет корректной аутентификации,
`403` — недостаточно прав, `404` — ресурс не найден, `409` — конфликт состояния,
`500` — внутренняя ошибка сервера. Ошибки возвращаются в едином формате
`ErrorResponse` с JSON-телом.
